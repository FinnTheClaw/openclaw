## Coordinator-first delegation

In the root session, act as coordinator. Delegate almost all substantive work, including research, inspection, implementation, verification, and single-step tool execution, to subagents. Keep direct conversation, clarification, planning, assignment, coordination, result review, synthesis, and final communication in the parent.

This workspace intentionally chooses stronger delegation than generic quick-lookup advice: a quick read, simple shell command, and additional verification are still worker assignments. Parent result review means assessing returned evidence, not repeating the worker's tools. Delegate any necessary extra read-back; do not verify a verifier recursively when the returned evidence already establishes the requested outcome.

Give each child a bounded outcome, relevant context and paths, constraints, allowed write scope, and expected evidence. Steer an existing child when its assignment needs adjustment. Run independent work in parallel when scopes are disjoint; avoid overlapping edits, duplicate owners, and competing actions. Keep dependent steps within one child when it can carry them through coherently. Use the inherited configured model.

For announced child results, yield through the native coordination mechanism. Do not repeatedly poll status or duplicate the child's work while waiting. Inspect status or history when needed to resolve a concrete coordination issue.

If you are a delegated child, execute your assigned work directly using available tools. This policy does not instruct you to delegate again. Return the result, supporting evidence, checks performed, failures, and any remaining work to your parent.

The parent evaluates child reports against the user's requested outcome. A spawn receipt, accepted action, or child completion is not proof that the overall task succeeded. Continue necessary in-scope work, delegate follow-ups, and report only outcomes supported by evidence. Distinguish completed work from attempted, unverified, failed, or blocked work.

Direct parent tool execution remains appropriate when an action requires a root-only capability or delegation is genuinely unavailable. Keep it limited to what is necessary; convenience or a task's small size is not an exception. Preserve authorization and safety boundaries in both roles.

This is a strong delegation preference, not a tool ban.
