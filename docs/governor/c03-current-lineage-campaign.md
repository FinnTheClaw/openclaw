# C03 deep productive-loop current-lineage campaign

## Status

`c03-deep-productive-loop@v1` is a compiled, default-off modular governor feature. It is inert
without its exact lowercase id, version, and `enforce` selection; it neither self-activates nor
changes an unselected governor. Historical C03 evidence remains campaign-accounting evidence, not
a release result.

The accepted historical behavior is an exact 24-turn durable trace: twenty canonical unique
successful observations, one transient failure followed by one non-guidance replan and retry, one
premature-finish rejection, then exactly one post-success aggregate. Every physical action has one
paired effect and outcome; no invented key, duplicate label, orphan outcome, count drift, or
reordering is allowed. The current lineage has the shared selected-module catalog and host route;
C03 adds only its narrow policy configuration to that existing seam.

## Missing skeleton capability

The skeleton must supply one feature-neutral production-owned governed-run consumer with a single
activation owner. It must atomically validate selection prerequisites before any enforcement, hold
one record per runtime identity across startup/freeze/close/survivor paths, preserve reverse
dependency cleanup, and be inert for `modules: []`. C03 must receive a narrow durable-loop
capability from that consumer and must not construct or configure the legacy lifecycle.

## Deterministic source gate

Every one of the 100 cases contains its complete expected 24-turn trace. The validator requires
turns 1–24 in exact order, canonical labels `observe-01` through `observe-20` exactly once on
success, an immediately adjacent failure→non-guidance-replan→same-key retry sequence, one
incomplete-finish rejection, and the aggregate as turn 24. Explicit negative oracles reject
duplicate labels, invented keys, missing action/effect/outcome pairing, changed order/value, and
wrong event count. This validates campaign data and complements the selected-module source
lifecycle proof; it is not installed C03 certification.

## Alistar acceptance protocol

1. After the skeleton seam and selected C03 module independently pass review, reboot through the
   unchanged PXE path and state-preservingly reprovision Alistar with the exact signed artifact.
   Use the installed agent, dedicated no-side-effect scope, supplied observation tool, configured
   coordinator route, and actual local Qwen backend; mocks, replay, and provider shims do not count.
2. Run every case once. Retain artifact digest, request/correlation ids, model/backend evidence,
   module identity, the full ordered action/effect/outcome trace, plan/replan versions, finish
   decisions, aggregate identity, and restart evidence.
3. Compare the captured trace to that case's exact expected trace with the same validator. A pass
   requires no error oracle, including after restart. Restart cannot double-close a runtime,
   silently reuse a closed runtime, duplicate an outcome, or change any pre-restart trace identity.
4. Require 100/100 passes, backend corroboration for every request, no unexpected gateway or
   coordinator error, and Alistar memory samples before/during/after. Any failure returns C03 to
   development with no promotion-ledger entry.
