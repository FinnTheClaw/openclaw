# C03 deep productive-loop current-lineage campaign

## Status

This is an inert campaign preparation, not a C03 module or release candidate. It cannot select,
activate, close, or alter a governor. Historical C03 evidence is accepted for campaign accounting,
but the modular reconstruction remains source NO-GO.

The accepted historical behavior is a 24-turn durable productive loop: twenty unique successful
observations, one transient failure retried once, one non-guidance replan, exactly one aggregate,
no invented key or duplicate/orphan outcome, and premature finish rejection before certified finish.
The reconstructed modular lifecycle is not eligible because prior reviews found split lifecycle
ownership and duplicate runtime-identity cleanup; current `948b` still has an empty module catalog
and only the broad legacy host route.

## Missing skeleton capability

The skeleton must supply one feature-neutral production-owned governed-run consumer with a single
activation owner. It must atomically validate selection prerequisites before any enforcement, hold
one record per runtime identity across startup/freeze/close/survivor paths, preserve reverse
dependency cleanup, and be inert for `modules: []`. C03 must receive a narrow durable-loop
capability from that consumer and must not construct or configure the legacy lifecycle.

## Deterministic source gate

The paired test locks a 100-case corpus: five classes of twenty cover baseline, one transient retry,
one non-guidance replan, premature-finish rejection, and restart/lifecycle recovery. All cases
require twenty unique successful observations and one aggregate. It validates corpus data only;
it is not C03 source or installed-behavior certification.

## Alistar acceptance protocol

1. After the skeleton seam and selected C03 module independently pass review, reboot through the
   unchanged PXE path and state-preservingly reprovision Alistar with the exact signed artifact.
   Use the installed agent, dedicated no-side-effect scope, supplied observation tool, configured
   coordinator route, and actual local Qwen backend; mocks, replay, and provider shims do not count.
2. Run every case once. Retain artifact digest, request/correlation ids, model/backend evidence,
   module identity, ordered action/effect/outcome trace, plan/replan versions, finish decisions,
   aggregate count, and restart evidence.
3. A case passes only when its twenty success labels are unique/current, expected failure/replan or
   premature-finish behavior occurs exactly once where requested, no outcome is orphaned or
   duplicated, and one aggregate follows the required successes. Restart cannot double-close a
   runtime or silently reuse a closed one.
4. Require 100/100 passes, backend corroboration for every request, no unexpected gateway or
   coordinator error, and Alistar memory samples before/during/after. Any failure returns C03 to
   development with no promotion-ledger entry.
