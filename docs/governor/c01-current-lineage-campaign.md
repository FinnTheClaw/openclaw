# C01 proportional-planning current-lineage campaign

## Status

This is inert campaign preparation, not a C01 module or release candidate. It cannot select,
activate, close, or alter a governor. Historical C01 behavior is accepted for campaign accounting,
but modular reconstruction is source NO-GO.

The accepted historical behavior is proportional work classification: prompt-contained quick work is
direct and tool-free; focused, effectful, incident, or externally evidenced work has a contract and
plan before tool execution; deep work is selected above twelve estimated useful actions or above three
independent branches. Thoroughness is evidence-driven, not a tool-count target, and no rule may suppress
necessary tools or mandate an arbitrary count. Current `948b` has an empty module catalog and only the
broad legacy host route, so it has no current-lineage C01 implementation.

## Missing skeleton capability

The skeleton needs one feature-neutral, production-owned governed-run consumer that receives the
authenticated task classification before any native tool dispatch and exposes a single ordered
pre-tool decision/plan-certificate seam. It must be inert for `modules: []`, preserve the native path
when C01 is off, and permit C01 alone to classify a task and require a plan without constructing or
configuring the legacy lifecycle. A module lifecycle registry by itself cannot observe an ingress or
tool dispatch, so it cannot implement C01.

## Deterministic source gate

The paired test locks a 100-case corpus: five classes of twenty cover quick direct replies, focused
read-only discovery, a simulated action contract confined to an in-memory test record, thirteen concrete
useful subactions, and four named independent branches. The task facts—not hidden fixture labels—carry
the classification pressure. Prompts neither prescribe plan-before-tool behavior nor disclose the expected
class, and they never set a tool-count target. The test validates corpus data only; it is not C01 source
or installed-behavior certification.

## Alistar acceptance protocol

1. After the skeleton seam and selected C01 module independently pass review, reboot through the
   unchanged PXE path and state-preservingly reprovision Alistar with the exact signed artifact. Use the
   installed agent, a dedicated no-side-effect scope, supplied observation tool, configured coordinator
   route, and actual local Qwen backend; mocks, replay, and provider shims do not count.
2. Run every case once. Retain artifact digest, request/correlation ids, model/backend evidence, module
   identity, classification, whether a plan was required, plan-before-tool ordering, tool trace, and
   gateway/coordinator error evidence.
3. A quick case passes only with direct no-tool behavior. Each focused/deep case passes only when its
   classification is exact and the governor—not model-visible prompting—requires a plan containing
   objective/success condition/next discriminating action before its first tool dispatch. The simulated
   effect must remain confined to its disposable in-memory record; all other cases remain no-side-effect.
   Every named subaction or branch needs evidence, with no invented evidence or fixed tool-count policy.
4. Require 100/100 passes, backend corroboration for every request, no unexpected gateway or coordinator
   error, and Alistar memory samples before/during/after. Any failure returns C01 to development with no
   promotion-ledger entry.
